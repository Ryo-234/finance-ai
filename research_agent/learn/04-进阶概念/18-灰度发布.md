# 灰度发布 / 蓝绿部署 - "新菜先让 1% 客人试吃"

> ⏱ 阅读时间：1 分钟

## 是什么

新版本上线时，**先给一小部分用户**用，**没事再扩大到全量**。避免一次发布挂掉全站。

## 类比

饭店新出一道菜：
- ❌ 直接给所有客人上 → 万一难吃，**全店差评**
- ✅ 先给 1% 客人试吃 → 没人投诉 → **全店推广**

## 2 种常见策略

### 灰度发布（金丝雀发布 Canary Release）

```
新版本 v2 → 5% 用户
   ↓ 30 分钟观察
   ↓ 没问题
50% 用户
   ↓ 30 分钟观察
   ↓ 没问题
100% 用户
```

**金丝雀** = 矿井里用金丝雀探测瓦斯，**金丝雀先死 = 有危险**。金丝雀 = 5% 用户。

### 蓝绿部署（Blue-Green Deployment）

```
当前版本（蓝）100% 流量
   ↓
新版本（绿）部署好
   ↓
LB 切 10% 流量到绿
   ↓
切 50%
   ↓
切 100%（蓝完全下线）
```

**好处**：出问题 1 秒切回蓝（**回滚快**）。

## 你的项目里

**现在不用**（1 台服务器、单版本）。

**未来用 K8s** 时天然支持（用 Deployment 的滚动更新）：
```bash
kubectl set image deployment/api api=myapp:v2
# K8s 自动：先起 1 个 v2 pod → 测试 → 慢慢替换所有 v1 pod
```

## 关键点

- **没有 100% 安全的发布**（再多的测试也覆盖不了所有情况）
- **灰度能救你一命**：出问题只影响 5% 用户
- **可观测性是前提**：你得能监控到错误率上升

## 跟你的项目关系

- **现在用不上**（用户 < 100）
- **面试可以聊聊**：体现你有"生产级思维"
- **大厂必用**：阿里/字节/美团每次发布都是灰度

## 缺了会怎样

- **小项目**不会缺
- **中大项目**一次发布 = 100% 用户受影响 = **一次事故**

## 怎么用（云平台）

| 平台 | 灰度方式 |
|---|---|
| **Vercel** | Preview Deployment（PR 自动部署预览）|
| **Render** | 多个 Service + 流量分配 |
| **K8s** | Canary Deployment（Ingress + Service）|
| **阿里云 SAE** | 灰度发布（可视化界面）|
| **Nginx** | `upstream` 加权重（`server 10.0.0.1 weight=5;`）|

## 高级：Feature Flag（功能开关）

不用部署新代码，**配置开关**控制哪些用户用新功能：

```python
if feature_flag("new_ui", user_id):
    return new_ui_html()
else:
    return old_ui_html()
```

**好处**：秒级开关，不用部署。

工具：**LaunchDarkly**（付费）、**Unleash**（开源）。

## 常见坑

- **数据库迁移**：新版本改了表结构，老版本跑不动
  - 解决：**先扩字段（不删）**、**双写**、**分阶段**
- **回滚预案**：回滚 = 切回老版本，但老版本代码可能不兼容新数据
- **用户无感**：切换瞬间用户正在操作（用 session 标记 / 灰度按用户 ID）
