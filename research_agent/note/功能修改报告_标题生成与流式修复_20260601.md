## 二、会话标题自动生成

### 2.1 问题描述

左侧会话列表和顶部标题显示原始 `thread_id`（如 `a1b2c3d4`），用户无法区分不同会话。

### 2.2 实现方案

参考 DeerFlow 的 `TitleMiddleware` 设计模式，新建标题生成中间件。

**中间件架构**：

```
首轮对话完成
  → TitleMiddleware.after_agent() 触发
  → 检查: title 为空? 有 1 条用户消息? 有 AI 回复?
  → 是: 调用 LLM 生成 ≤15 字标题
  → 失败: 回退到用户消息前 20 字符 + "..."
  → 写入 state.title → chat.py done 事件携带 → 前端显示
```

**为什么用中间件而不是回调**：
- 解耦：标题生成不污染聊天业务逻辑
- 双钩子：同时挂载 `after_model` 和 `after_agent`，覆盖所有意图路径（任务/问候/澄清）
- 可配置：通过 factory.py 控制启用/禁用和参数

### 2.4 踩坑记录

1. **问候路径不触发 after_model**：问候意图在 planner 节点后直接结束，不经过合成节点。解决方案：同时重写 `after_agent` 钩子。

2. **after_agent 返回值被忽略**：`run_research` 中调用 `apply_after_agent` 但没合并返回值到 result。修复：`result = {**result, **agent_result.updates}`。

3. **问候路径无 AIMessage**：问候回复存在 `greeting_response` 字段而非 AIMessage。修复：`_check_and_generate` 兼容从 `answer`/`greeting_response` 提取 AI 上下文。

4. **_threads_meta 导入缺失**：chat.py 引用 threads.py 的 `_threads_meta` 但未导入。修复：添加 `from api.routers.threads import _threads_meta`。

## 三、SSE 解析重写

### 3.1 问题描述

前端流式输出内容被截断，浏览器控制台显示 chunk 数量远少于 curl 测试（3 个 vs 26 个）。

### 3.2 根因分析

旧解析器逐行匹配 `event:` 和 `data:` 配对。当 MiniMax 流式返回的某些 chunk 内容包含特殊字符或数据行被 TCP 分包时，`JSON.parse` 可能失败，导致后续事件丢失。

### 3.3 修复方案

用 SSE 标准解析方式——按 `\n\n` 双换行分割事件，再在每个事件内匹配 `event:` 和 `data:` 行。

```typescript
// 旧：逐行匹配
const lines = buffer.split('\n')
// 问题：data 行被截断时 JSON 解析失败

// 新：按 \n\n 分割事件
const events = buffer.split('\n\n')
buffer = events.pop() || ''  // 保留不完整事件
// 每个完整事件内再匹配 event: 和 data: 行
```

## 五、实习答辩话术

> "我独立实现了一个 TitleMiddleware 中间件，参考 DeerFlow 的设计模式。当用户发送第一条消息并获得回复后，中间件自动调用 LLM 生成一个简洁的会话标题，显示在侧边栏和顶部标题栏。
>
> 在实现过程中遇到了几个有意义的技术问题：第一个是问候意图不经过合成节点，after_model 钩子不会触发，我通过同时挂载 after_agent 钩子解决了这个问题。第二个是 run_research 中调用 after_agent 后忽略了返回值，导致中间件的更新无法传递到最终结果。第三个是流式输出内容被截断，我从逐行解析改为标准的 SSE 双换行解析彻底解决了。
>
> 这次实践让我深入理解了 LangGraph 中间件链的执行机制——中间件按 order 排序，依次执行 before_model → after_model → after_agent 钩子，每个钩子可以返回 MiddlewareResult 来修改状态。"
